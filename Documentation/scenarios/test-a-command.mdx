description: Test a Cratis Arc command in-process with substituted application services, checking both the pipeline result and the handler's intended work.
---

Test a Cratis Arc command through the in-process pipeline when you need to check validation and handler execution together. Supply a substitute application service, execute the command, then assert both success and the call made to that service. This checks the command's behavior without a web server or database.

## Use the standalone harness

Start with an application project and a test project that references it. For the C# example, reference `Cratis.Arc.Testing`, `Cratis.Specifications.XUnit`, `NSubstitute`, and the usual xUnit runner/test SDK. `Cratis.Testing` is the wider integration meta-package; it is not required here. A dedicated spec project can run in Debug and Release. Use `#if DEBUG` only for specs intentionally embedded in an application assembly that excludes them from Release.

On the JVM, add `io.cratis:arc-testing` as a `testImplementation` dependency, use JUnit 5, and make the application's generated `ArcArtifactModule` available to the test. The TypeScript example needs `@cratis/arc.testing` and Vitest. These are backend-specific harnesses, not interchangeable APIs; Cratis Chronicle is not needed for this service-backed example.

For decision-only cases, a direct `Handle()` call can be the simpler test. The [decision-and-pipeline lesson](/arc/backend/csharp/testing/command-decisions/) shows how the two approaches complement each other. This recipe deliberately tests service interaction through Arc.

`CommandScenario<TCommand>` runs the real validation, authorization, `Provide`, and handler pipeline. It does **not** automatically fake your Mongo collection, context, or application services. Register all collaborators before the first `Execute` or `Validate`; the service provider is built lazily then. Dispose the scenario afterward.

:::tip[Test the decision separately from execution]
On the C# backend, for immediate inline side effects, prefer [command operations](../backend/csharp/commands/operations/index.md); the direct service-call example below remains supported. An operation-returning `Handle()` can be tested by inspecting its data without executing the work. It is pure only when it uses supplied inputs without I/O, clock reads, randomness, or mutable external state. [Operation scenarios](../backend/csharp/testing/command-operations.md) test actual execution and recovery with controlled collaborators, not automatic recording stubs.
:::

## Assert the effect through the pipeline

Create the spec in the test project:

The first assertion checks the pipeline result. The second checks that the handler called its collaborator with the intended identifier and name. A success result alone would miss a handler that returned without registering anything. Neither assertion checks a production database mapping or index; test those at the storage integration boundary.

C# discovers the command from `CommandScenario<TCommand>` and exposes `IServiceCollection` for registrations. The spec disposes the scenario in `Destroy`.

The JVM harness uses the module generated by Kotlin Symbol Processing (KSP) and the command class, so generated wiring participates in the test. Register each collaborator with `addService(type, instance)` and call the suspending `execute` function; this harness needs no disposal. The example's hand-written service records calls rather than using NSubstitute.

TypeScript registers its recording fake in `scenario.services`, awaits `scenario.execute(...)`, and disposes the scenario with `await scenario.dispose()`.

Run the test with your project's configured runner. For C#, run `dotnet test` from the test project directory. Both assertions should pass, and the substituted service should record exactly the identifier and name supplied to the command.

## Check rejection independently

Add a separate spec with the same service setup but an empty author name. Expect validation failure and no registration call. On C#, assert `ShouldNotBeSuccessful()` and `ShouldHaveValidationErrors()` and verify that `Register` was not called. On the JVM, chain `shouldBeAuthorized().shouldBeInvalid()` to distinguish validation rejection from authorization failure.

Use `Validate` / `validate` in a separate spec when you only want pre-flight validation. It does not invoke the handler, so it cannot check service interaction.

If the success spec reports an unresolved dependency, register it before the first pipeline call. If the empty-name spec succeeds, check that the command's validator is included in discovery or passed to the scenario as required by your backend.

For protected commands, set up the principal explicitly and assert `ShouldNotBeAuthorized()` / `shouldBeUnauthorized()` separately from validation. The [scenario reference](/arc/backend/csharp/testing/command-scenario/) and the [JVM in-process testing guide](/arc/backend/kotlin/guides/testing/) cover context setup and the complete assertion API.

## Optional Chronicle testing

For an event-sourced command, use the [Chronicle testing extension](/arc/backend/csharp/testing/chronicle/) to seed events or read models and assert appends. That tests Chronicle integration behavior; the standalone recipe above checks a call to an application service and makes no claim about persistence.
