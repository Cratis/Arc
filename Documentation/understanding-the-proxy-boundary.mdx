Every full-stack app has a seam down the middle: C# on one side, TypeScript on the other, HTTP in between. Normally *you* are the glue across that seam — you write a controller, hand-write a DTO, redeclare its shape in TypeScript, wrap it in a `fetch`, and then spend the rest of the project keeping both sides in agreement. Nothing tells you when they drift: a renamed field compiles happily on each side and fails in the browser at runtime.

Arc removes that seam. You write the command or query **once, in C#**, and the build generates the TypeScript your frontend calls. There's no second declaration to keep in sync, because there's no second declaration at all. This page is about *why that works* and *what keeps it honest* — the idea at the center of everything Cratis calls "full-stack type safety."

## One source of truth

The thing to internalize: **your C# command and query records are the contract.** The TypeScript proxy isn't a parallel definition you maintain — it's a *projection* of the C# types, regenerated by a configured proxy-generation build. There is exactly one place the shape of `RegisterAuthor` is defined, and it's the C# record.

```mermaid
flowchart LR
    CS["C# record — [Command] RegisterAuthor"] -->|Debug build · post-build assembly/PDB tool| TS["generated TS proxy — RegisterAuthor"]
    TS -->|import + call| RX["React — CommandDialog · .use()"]
    RX -.->|HTTP — typed both ends| CS
```

Generating from the same types catches structural drift at compile time when you rebuild and type-check both sides. It does not prove that a deployed client matches a deployed server, that runtime serialization customizations agree, or that build-time routes match runtime configuration. Those still need integration checks.

## Walk the boundary

1. **Write the slice on the backend.** A command is a record (C#) or a data class (Kotlin) with a handler on it. This standalone excerpt uses the [tutorial's domain types, imports, and provider setup](/arc/backend/csharp/getting-started/your-first-command/):

   <ArcBackendTabs snippet="understanding-the-proxy-boundary/register-author" />

2. **Configure and build.** Each backend discovers commands, queries, referenced types and supported validation rules from your own code during its ordinary build, then writes the TypeScript. How it reads your code differs, and so does where generation can be switched off.

   On **C#**, install `Cratis.Arc.ProxyGenerator.Build` and set `CratisProxiesOutputPath` as in [generator setup](/arc/backend/csharp/proxy-generation/getting-started/), then run `dotnet build -c Debug`. An MSBuild target runs after the build and invokes a **post-build executable** that inspects the compiled assembly and its PDB — it is not a Roslyn source generator. Without an output path the target does nothing, which is also how you skip generation on a second build.

   On **Kotlin and Java**, apply the `io.cratis.arc` Gradle plugin and configure `cratisArc { proxies { } }` as in [TypeScript proxies](/arc/backend/kotlin/guides/typescript-proxies/). A **KSP annotation processor** runs as part of compilation and records what it found in an artifact manifest, and the `generateArcProxies` Gradle task turns that manifest into TypeScript.

   Namespace folders, source-file placement, and index output depend on each backend's generator configuration.

3. **Import the proxy in React.** It's already there, generated from the backend code above — call it as if it were local, typed code:

   ```tsx
   import { RegisterAuthor } from './Authors/RegisterAuthor';   // generated

   // Form fragment: retain the imports/providers and per-operation id state
   // from the first-slice tutorial; mount a new dialog instance per registration.
   <CommandDialog<RegisterAuthor> command={RegisterAuthor} title="Add author" initialValues={{ id }}>
       <InputTextField<RegisterAuthor> value={i => i.name} title="Name" />
   </CommandDialog>
   ```

## What keeps it honest

Here's the payoff — and the whole reason the boundary is *generated* rather than written. Suppose you rename the name property on the command:

<ArcBackendTabs snippet="understanding-the-proxy-boundary/rename-property" />

Rebuild, and the generated proxy has `fullName` where it used to have `name`. The React component that still reads the old property stops compiling — caught at build, not in production:

```tsx
// This line stops compiling until you fix it:
<InputTextField<RegisterAuthor> value={i => i.name} title="Name" />
//                                         ^^^^ Property 'name' does not exist on RegisterAuthor
```

You didn't run the app. You didn't open the browser. After regeneration and a frontend type-check, the TypeScript compiler catches the drift, because the accessor `i => i.name` points at a property the regenerated type no longer has. That's the difference between a generated boundary and a hand-written one: drift is a **compile error**, not a **production incident**.

<Aside type="note" title="The read side is just as honest">
Rename a field on a `[ReadModel]`, rebuild, and every component reading it through the generated query proxy stops compiling the same way. The contract holds in both directions — commands you send and data you read.
</Aside>

## What gets generated

A configured generator build can emit:

- **Commands** — a class you instantiate and execute (or hand to a `CommandDialog`), with every parameter — route, query string, body — flattened into typed properties.
- **Queries** — a proxy exposing a React `.use()` hook that returns the typed result with its loading and error state; **observable** queries return a live subscription that re-renders on change — no polling, no manual refresh.
- **Types and enums** — every complex type and enum your commands and queries reference, so nested shapes are typed too.
- **Identity details** — your custom identity type, so the signed-in user is typed on the frontend.

Each has a detailed reference: [Commands](/arc/backend/csharp/proxy-generation/commands/), [Queries](/arc/backend/csharp/proxy-generation/queries/), and [Identity details](/arc/backend/csharp/proxy-generation/identity-details/). The [frontend proxy-generation guide](/arc/frontend/react/proxy-generation/) shows the generated TypeScript for each, with the `.use()` and `useSuspense()` hooks.

<Aside type="note" title="Not every backend return value crosses the boundary">
On the C# backend, [command operations](./backend/csharp/commands/operations/index.md) describe inline work for the server, not the browser. The proxy generator excludes operations and operation batches from the client response contract. React still executes the generated command and handles its ordinary result; compensation and recovery observations remain backend concerns.
</Aside>

## The transport disappears too

Types are only half of what the proxy absorbs. The other half is **how the call travels**. Your component never writes a URL, picks an HTTP verb, or opens a socket — it executes `RegisterAuthor` or renders `AllAuthors.use()`, and the proxy owns the wire. That makes the transport an implementation detail behind the boundary: today the calls ride HTTP, and if Arc carried them over something else — gRPC-Web, say — the proxy is where that would change, not your components.

The query system already cashes in on this freedom. A regular query executes as a plain HTTP request. An observable query streams — over WebSockets or Server-Sent Events, a choice you make once with the `queryTransportMethod` prop on the [`<Arc/>` context component](/arc/frontend/react/arc/), not in any component. And the same observable query can still be executed as a one-shot HTTP fetch by calling `perform()` on the proxy, when you want a snapshot instead of a subscription:

```tsx
const [authors] = AllAuthors.use();                  // live — streams over WebSockets or SSE
const snapshot = await new AllAuthors().perform();   // one-shot — a plain HTTP fetch, same proxy
```

One definition in C#, one proxy in TypeScript — and whether the data arrives as a response or a stream is the proxy's concern, not yours. Tune the live transport in the [query configuration reference](/arc/frontend/react/queries/configuration/).

## It's a build step, not a runtime discovery call

A few things follow from the proxies being *generated*, and they're worth holding onto:

- **You never edit a generated file.** Treat the generated folder like build output — change the C#, rebuild, and the TypeScript follows.
- **The generator tracks what it made** and removes files for commands or queries you delete, so the generated tree doesn't accumulate ghosts. (See [File index tracking](/arc/backend/csharp/proxy-generation/file-index-tracking/).)
- **The sequencing is fixed:** backend compiles → proxies generate → the frontend can reference them. For a single slice you can't build the React half before the C# half compiles — which is exactly why the workflow is backend-first.

## Why this is the thing that matters

Plenty of frameworks give you CQRS, or an event store, or a component library. The proxy boundary is what makes Cratis **full-stack**: the type safety doesn't stop at the edge of the backend — it runs all the way to the React component. It's why a Cratis feature is *one* thing expressed in two languages, kept in agreement by the build instead of by discipline.
