Our back office works, but it's wide open: anyone who can reach it can register authors and add books. The last thing a real app needs is to decide *who is allowed*. We'll add role-based authorization — and the nice part is that it's declarative, so none of our `Handle()` methods or read models change. The rule lives at the boundary, where it belongs.

## Prerequisites

Continue with the standalone ASP.NET Core host from [chapter 1](/arc/tutorial/first-slice/). Add `global using Cratis.Arc.Authorization;` to `GlobalUsings.cs`; on the JVM, import `io.cratis.arc.authorization.Roles` in the files that use it. This chapter uses the literal role name `"Librarian"`; it must match an authorization role on the authenticated principal. No domain enum or identity-details provider is required.

## Gate the commands

Authorization is a cross-cutting concern. You don't want `if (user.IsLibrarian)` checks scattered through your logic — you want one declaration at the edge. Put `[Roles(...)]` — `@Roles(...)` on the JVM — on the command, and Arc checks the caller's roles before the command runs. On both backends the operation's own declaration wins over the class's. That is what lets a protected read model still expose one open query — on the JVM an operation that declares `@AllowAnonymous`, `@Authorize`, or `@Roles` replaces the class default entirely rather than merging with it, so narrowing is exact. <Aside type="note" title="The frontend respects it too">
The server enforces these rules for calls from generated proxies and other clients alike; proxies surface the authorization result. So you can drive your UI off identity as well: hide the "Add author" button when the signed-in user isn't a librarian, and the command is *still* protected on the server if someone calls it anyway. See [frontend identity](/arc/frontend/react/identity/) for reading the current user's roles in React.
</Aside>

## Where the roles come from

Arc checks `ClaimsPrincipal.IsInRole("Librarian")`. Configure your authentication scheme's role claims accordingly. An application detail such as `LibraryIdentity.Role` does **not** grant that role: `IProvideIdentityDetails` enriches client/domain context, and its rejected result controls `/.cratis/me`, not every operation.

The JVM asks the same question of an `ArcPrincipal`: a caller holds `Librarian` when one of its roles is that name, which is what a Spring Security `ROLE_Librarian` authority becomes once Arc drops the prefix. An `IdentityDetailsProvider` plays the same enriching, non-granting role there as `IProvideIdentityDetails` does here.

The rest of this section is the .NET host's development fixture and has **no JVM equivalent to copy**. For this **loopback-only development checkpoint**, configure the trusted-header authentication adapter before `builder.Build()`:

```csharp
if (builder.Environment.IsDevelopment())
{
    builder.Services.AddMicrosoftIdentityPlatformIdentityAuthentication();
}
```

Before `app.UseCratisArc()`, add:

```csharp
if (app.Environment.IsDevelopment())
{
    app.UseAuthentication();
}
```

Keep the host bound to `http://localhost:5000` as in setup. Follow [Generate a local principal](/arc/backend/csharp/development/generating-principal/) to send the three `x-ms-client-principal` headers through the local Vite proxy. In that page's JSON, include `"Librarian"` in `userRoles`, then Base64-encode that JSON locally. Restrict the browser header override to your localhost app URLs.

This adapter **does not validate bearer-token signatures, issuer, or audience**. It trusts the headers. Production must instead use a properly configured authentication scheme or an authenticated trusted ingress that replaces spoofable headers and prevents direct backend access. Never expose this local header-spoofing fixture publicly.

<Aside type="caution" title="Signing in on the JVM">
Do not translate the two snippets above. A Spring Boot host authenticates through its own ordered `AuthenticationHandler` beans (or `AsyncAuthenticationHandler` from Java), each returning anonymous, failed, or an `ArcPrincipal` carrying the caller's roles — a handful of lines is enough to sign in a development user with `"Librarian"` in its role set. The JVM does ship a platform-identity bridge that reads the same `x-ms-client-principal` headers, but it is **off by default**, requires `cratis.arc.platform-identity.enabled=true`, and refuses every submission until you supply an `ArcPlatformIdentityTrust` bean that verifies your ingress strips caller-supplied headers. Start with [Authenticate and authorize Arc endpoints](/arc/backend/kotlin/guides/security/) and register a handler of your own.
</Aside>

## Verify permissions, not just UI visibility

Rebuild, restart, and test these separately. The checks are the same on both backends; only the way you present a principal differs — the headers below for the .NET fixture, whatever your JVM authentication handler accepts otherwise:

1. Without identity headers, protected commands and queries must reject access.
2. With a valid local principal but no `Librarian` role, they must still reject access.
3. With `Librarian` in `userRoles`, list authors and register one successfully.
4. Remove the role again. Hiding a button is optional UI behavior; a direct operation call must still fail.

Inspect `isAuthorized` on the command/query result. Authentication middleware may reject a request before an Arc result is created, so also inspect the HTTP response. The recap below assumes you observed all three principal cases, not merely added attributes.

For production authentication and domain details, continue with [Identity](/arc/backend/csharp/identity/) and [Authorizing commands and queries](/arc/backend/csharp/authorizing-commands-and-queries/), or with the JVM's [security guide](/arc/backend/kotlin/guides/security/).

## Look back at what you built

Five chapters ago we had nothing. Now we have a real full-stack library back office, running over a plain database — and you've used every part of the Arc loop and know *why* each one is shaped the way it is:

- **Chapter 1** — a full-stack slice: a `[Command]`/`@Command` with a handler that writes, a `[ReadModel]`/`@ReadModel` with its query, and a React screen calling both through generated, typed proxies — the same TypeScript whichever backend generated it.
- **Chapter 2** — trust: a `ConceptValidator` on the value type and a `CommandValidator` business rule, both surfaced in the UI through the generated proxy.
- **Chapter 3** — relationships: a second slice and a filtered query that reads one author's catalog, no join.
- **Chapter 4** — life: observable queries as standing subscriptions, database to browser.
- **Chapter 5** — authorization: `[Roles(...)]` at the boundary, on both commands and queries, tied to the signed-in user.

The thing worth taking with you is the loop itself: **something happens (a command) → it writes state → that state is served (a query) → and React calls all of it, typed end to end.** Every feature you build from here is another turn of that loop in its own folder. You never go back and edit the last one to add the next.

And notice the boundary you proved: Arc did not need an event store for this CQRS loop. That is not an argument against event sourcing. For information systems, we usually reach for Chronicle as the default because history pays for itself. The point is architectural independence: CQRS can run over a plain database, and event sourcing can run without Arc, but they fit together extremely well.

From here, build another feature the same way, or take the next layer up: [Components](/components/) turns these generated commands and queries into higher-level screens, and the [Cratis Stack tour](/cratis-stack/) shows where Arc fits with the rest of the platform.
