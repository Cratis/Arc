We left chapter 1 with a working slice and an honest problem: a librarian can register an author with a blank name, or the same author twice, and nothing stops them. A trustworthy app has to be able to say *no* — clearly, and as early as possible.

There are two different kinds of "no" here, and Arc handles them in two different places:

- **"That input is malformed."** A blank name is wrong on its face — you don't need to look at anything else to know it. That's a *validation* rule, and it belongs on the value.
- **"That input collides with what already exists."** A duplicate name is only wrong relative to the rest of the system. That's a *business rule*, and it needs to consult state.

Let's add both. This chapter extends the files and imports from [chapter 1](/arc/tutorial/first-slice/). Put each validator in its own file under `src/Authors/` with `namespace Library.Authors;`; choose the same database branch. On the JVM, put each validator in its own file in the same package as the command and mark it `@Component` so Spring registers it. Name comparison is exact in this lesson, not case-folded or normalized.

## Validate the value, once

Your first instinct might be to validate `Name` inside a `RegisterAuthor` validator. But think about it: *every* command that takes an `AuthorName` wants the same guarantee — never blank. Arc lets you state that rule **on the value type itself**, so it's enforced everywhere an `AuthorName` is used, and you never write it twice.

<Steps>

1. **Write a `ConceptValidator` for the value type.** On C# it reaches into the concept's underlying `Value` and applies ordinary [FluentValidation](https://docs.fluentvalidation.net/) rules; on the JVM it implements Arc's `ConceptValidator` interface and reads the same underlying value through `value()`:

   <ArcBackendTabs snippet="tutorial/validation/author-name-rule" />

   That's the whole change. C# discovers the validator by convention, with no registration at all; the JVM one is an ordinary Spring bean, so `@Component` is all the wiring it needs. From then on, any command carrying an `AuthorName` rejects a blank one before the handler ever runs.

</Steps>

## Reject the duplicate against existing state

Uniqueness is the harder kind of "no", because it depends on what's already there. Input validation can't answer it — you have to look in the database. That's a job for a **`CommandValidator`**, which validates a whole command and, because Arc constructs it from the container, can take the dependencies it needs to check state.

<Steps>

1. **Write a `CommandValidator` that asks the database.** Both backends take the dependency they need and look for an author already carrying this name; if one exists, the command is rejected:

   <ArcBackendTabs snippet="tutorial/validation/duplicate-name-rule" />

   The two shapes genuinely differ, and it is worth seeing why. C# expresses the lookup as FluentValidation's `MustAsync` predicate. Arc.Kotlin has no async predicate rule to reach for — its shared fluent surface is deliberately limited to literal rules — so the JVM sibling is the plain imperative `CommandValidator` bean, whose `validate` is already a suspending function and can simply await the repository. Both return the same rejection to the same caller.

   The handler doesn't change — `Handle()` on C#, `handle` on the JVM, both still the clean write from chapter 1. The validator runs first; if it fails, the handler never executes.

   **On the relational branch**, the C# validator injects the context instead of the collection:

   ```csharp
   public class RegisterAuthorValidator : CommandValidator<RegisterAuthor>
   {
       public RegisterAuthorValidator(LibraryDbContext db)
       {
           RuleFor(c => c.Name)
               .MustAsync(async (name, ct) => !await db.Authors.AnyAsync(a => a.Name == name, ct))
               .WithMessage("An author with that name is already registered.");
       }
   }
   ```

   The JVM validator is unchanged by that choice: it already asks a repository, and which Spring Data module backs that repository is not its business.

</Steps>

## Install the database constraint

A check-then-write has a race: two registrations can both pass validation. The validator supplies the friendly message; the database must enforce uniqueness independently.

<Tabs syncKey="db">
<TabItem label="MongoDB" icon="seti:db">
Add this block to `Program.cs` after `app.UseCratisArc()` and before `RunAsync()`:

```csharp
using (var scope = app.Services.CreateScope())
{
    var authors = scope.ServiceProvider.GetRequiredService<IMongoCollection<Author>>();
    await authors.Indexes.CreateOneAsync(new CreateIndexModel<Author>(
        Builders<Author>.IndexKeys.Ascending(author => author.Name),
        new CreateIndexOptions { Unique = true, Name = "unique_author_name" }));
}
```

Restart the host and require index creation to succeed. Existing duplicate names must be resolved first; do not ignore an index-creation failure. This uses the configured collection and concept serializer rather than guessing stored field names.
</TabItem>
<TabItem label="EF Core" icon="seti:db">
Add this override to `LibraryDbContext`:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    base.OnModelCreating(modelBuilder);
    modelBuilder.Entity<Author>().HasIndex(author => author.Name).IsUnique();
}
```

For the **disposable SQLite tutorial database**, stop the host, remove only `Library/library.db`, and restart so `EnsureCreatedAsync` creates the new schema. This loses tutorial data; re-register the authors afterward. For retained data, create/apply a migration instead. `EnsureCreatedAsync` never upgrades an existing database.
</TabItem>
</Tabs>

The JVM has no Arc-specific step here either, because the constraint belongs to the store rather than to Arc: create the unique index through your Spring Data MongoDB mapping or index operations, or through a JPA unique constraint applied by your schema tooling. The reasoning above is unchanged — the validator gives the friendly message, and the index is what actually holds under a race.

<Aside type="caution" title="A race is not automatically a validation result">
The unique index prevents the second write, but this lesson does not translate a provider duplicate-key exception into a field validation message. A racing loser can receive an exception result. Production code should catch only the specific duplicate-constraint violation and translate it to a typed validation failure; unrelated storage failures must remain errors. Moving the same pre-check into `Handle()` would not make it atomic.
</Aside>

## The UI already knows

Here's the part that feels like a gift. You didn't touch the React code from chapter 1 — but the form now validates.

When you wrote the `ConceptValidator`, the C# proxy generator extracted that rule into the generated TypeScript too, so the `CommandDialog` runs it **on the client** and disables the confirm button on a blank name — no round trip. The uniqueness rule can't run on the client (it has to look in the database), so it runs on the server; when it rejects, the message comes back through the same proxy and `CommandDialog` renders it against the form — *"An author with that name is already registered."* — because the dialog wires command results to fields for you.

:::caution[Client-side rules are declared differently on the JVM]
The server half of this is identical on both backends, and so is the form: a rejected command comes back through the same generated proxy and lands on the same field. The **client** half is not. An imperative Kotlin `ConceptValidator` or `CommandValidator` is server-only; registering the bean does not invent a TypeScript rule. To have the blank-name rule run in the browser too, declare it as a literal rule in a [`FluentModelValidator`](/arc/backend/kotlin/guides/validation/), which KSP does extract into the generated validator. That surface is bounded on purpose — literal string, collection, and numeric rules, no predicates and nothing asynchronous — so a rule like uniqueness stays server-side on both backends anyway.
:::

This is a fragment of `AddAuthor` from chapter 1; retain its imports and per-operation `const [id] = useState(() => Guid.create())` initialization. Mount a new dialog instance for each registration.

```tsx title="AddAuthor.tsx — form fragment"
<CommandDialog<RegisterAuthor> command={RegisterAuthor} title="Add author" okLabel="Add" initialValues={{ id }}>
    <InputTextField<RegisterAuthor> value={i => i.name} title="Name" />
</CommandDialog>
```

One rule on the value type, one rule on the command, and both ends of the app honor them — because the validation, like the types, flows from one source.

## Verify the rejection paths

Rebuild the backend to regenerate validation metadata — `dotnet build -c Debug`, or `./gradlew generateArcProxies` on the JVM — then run the frontend type-check/build. Open a new dialog: blank Name must keep confirmation disabled. Submit a new name successfully; open another dialog and submit that exact name again. Expect a server validation message and no additional row. Confirm the unique index/schema step succeeded separately — a friendly duplicate rejection alone does not prove concurrency protection.

## What you built

- An `AuthorNameValidator` that guards the **value type**, enforced everywhere an `AuthorName` is used — and, on C#, also run client-side through the generated proxy.
- A `RegisterAuthorValidator` **business rule** that checks existing state in the database, with a unique index behind it for the hard guarantee.
- A React form that surfaces every server rejection with no extra frontend code, plus the client-side rules the backend chose to share.
